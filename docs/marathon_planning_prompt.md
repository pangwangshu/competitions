# Marathon 开赛规划提示词

基于 `tc_marathon_166/report/writeup.md` 和 `tc_marathon_167/report/writeup.md` 的 §9–§11 总结。下次比赛开始时，把最后一节的提示词整段贴给 AI Agent。

## 两场的共同错误

- **MM166 (HexTiles，55/75，约为冠军分数的 0.52 倍)**
  - 太晚才读生成器，也太晚才审计指标。早期记录的"大盘面匹配率 21–31%"后来无法复现，却决定了很长时间的优化方向。
  - 没有搞清楚目标函数的形状。得分是 F = K×V，两个因子相互影响。
  - 把大部分时间花在对一个架构的 tuning 和加速上。pair-by-pair 的局部改进（route library、path upgrade）都输了。
  - 最后一天的 10 个挑战者都没能过发布门槛，调参已到平台期，但此时已无法更换架构。
  - 没有为备选架构（C++ 版、全局朝向搜索、联合修复）预留时间。
- **MM167 (WordGame，约为冠军分数的 0.47 倍)**
  - 贪心 baseline 的日志已经显示"每个消耗的 tile 的得分在牌堆后段下降"，这个分析一小时就能做完，却没有在第一晚做。
  - 它本可以指向"jackpot / 乘数格"这一核心结构，但直到最后才想到跨回合的持久目标规划。
  - 之后都是在 greedy + 2-ply 上叠加 prefilter、rollout 和 fishing，后来饱和；局部 +2.9%，线上 −2.4%。
  - 166 的教训"先推导理想解的样子，再选算法"在 167 里没有被执行。
- **共同模式**
  1. baseline 一出来就跳进优化。
  2. 没有先做得分解剖（score anatomy）。
  3. 架构和表示（语言、数据结构、候选生成、决策单元）被过早锁定。
  4. 局部指标和线上指标不一致，本地验证集被反复用来调参。
  5. 没有给"替换架构"的实验预留时间。

## 建议流程

1. 读规则和生成器，推导理想解的结构。
2. 做 baseline，只做测量，不优化。
3. 做得分解剖，找出哪些因素主导分数。
4. 先写出"难以回头"的决策清单，逐项做小实验并选定，再进入迭代。
5. 提前定好决策门槛和时间预算。
6. 之后再做迭代，用 paired 比较、新种子确认。
7. 每个阶段回头检查："这是在调参，还是该换架构？"

## 可直接贴进去的提示词

```
你是我在 TopCoder Marathon Match 中的 AI Agent。在开始写任何优化代码之前，请先遵守下面的规划纪律。这些规则来自我在 MM166 (HexTiles, 55/75) 和 MM167 (WordGame, 得分约为冠军的 0.47 倍) 中犯过的错误。两次的共同问题是：baseline 一出来就跳进局部优化，到后期才发现架构或目标结构选错了，来不及改。

## 阶段 0：理解问题（不写求解器）
1. 完整读题面、评分函数、官方 tester 和（若有）数据生成器。用自己的话写出评分公式，并写出"一个改动 ΔScore 由哪些项组成"，说明各项如何互相影响（例如 F = K×V 会让两个因子耦合）。
2. 推导"理想解长什么样"：分数是被少数几个事件主导（乘数、jackpot、长路径），还是被大量小事件累积？先给出假设，再用数据验证。
3. 列出输入的规模、参数和分布，以及时限、CPU 核数和语言限制。
4. 把隐藏的可行解、oracle 或知道未来信息的启发式只当作诊断工具，不要当作上界。

## 阶段 1：baseline 只做测量，不急于优化
1. 实现最简单的合法 baseline，并用官方 tester 逐字节复核输出。
2. 在不同规模和参数上跑 baseline，保存所有输入输出和日志。
3. 做"得分解剖"，写出结论：
   - 分数按阶段、规模、事件类型的分布（例如前 1/4 与后 1/4 每个资源的得分率）。
   - 各个分量的占比（匹配数、路径价值、惩罚、主导路径占比等）。
   - 与天真上界或反事实的对比，只作量级参考，不当作预测。
   - 审计每个分母和指标的定义，并人工检查若干实际输出，避免错误诊断定义整个优化方向。
4. 在得分解剖完成前，禁止调参、加速和加入新的启发式。

## 阶段 2：先决定"之后很难再改"的东西
在进入迭代前，写一份决策清单，并为每一项做小规模的对照实验，数据达标才锁定：
- 决策单元：是单步动作，还是跨回合的计划或目标（持久目标、骨干路径、整体朝向）。
- 状态表示和评估函数：是否支持增量评估，评估是否需要看整个盘面或全局结构。
- 初始化方式：廉价构造、软骨干（只是提示，可被打破）、随机起点之间的对比。
- 邻域和搜索算子：是否包含联合修复或多对象的协同邻域，还是只有局部的单对象改动。
- 语言和性能：先测量吞吐（每秒评估次数）和每次评估的成本，再决定是否用编译型语言重写。保留慢实现作为 oracle。
- 时间模型：用可复现的工作量单位计预算，并配上墙钟保护；重操作内部要有抢占点；留出输出时间。
- 评估协议：本地数据集、新种子、官方反馈各自能回答什么问题，要提前说明。
每个候选架构至少要有一个"便宜的原型 + 等时间或等工作量的对比"。如果没有任何一个架构比 baseline 的简单增强更好，要明确写出这个结论。

## 阶段 3：迭代
1. 只有阶段 2 的决策被冻结后才开始 tuning，并写下发布门槛，例如"相对当前最佳在 100 个新种子上至少提升 2% 且零失败"。
2. 每一次改动都要保留：配对比较、胜负数、按规模和参数分片的结果、运行时尾部。每个 commit 都用冻结的 oracle 或 golden trace 校验。
3. 用于诊断某个失败的测试集，从此是开发数据；确认修复要用没碰过的新种子。
4. 对每个提案要先问："这是在优化当前架构的参数，还是在逼近当前架构的上限？"如果连续几个挑战者都过不了门槛，或者宽度、样本、时间这些维度都已饱和，就停止 tuning，回到阶段 2 重新评估架构或价值函数。
5. 不要把"回归到 baseline 的局部赢"当成成功：局部提升和线上结果方向不一致时，先查原因（时限尾部、单核、归一化到变化的 MAX），不要继续叠加。
6. 每个负面结果都要记录数据和结论，写入日志。

## 时间纪律
- 前约 25% 的时间：阶段 0、1，并完成阶段 2 的大部分对照实验。
- 中间约 50%：在选定架构上迭代；每次迭代前复查是否应该换架构。
- 最后约 25%：只做经过验证的改动、冻结提交包（记录 hash、配置和提交 ID）；不再尝试大型新想法。
- 若在 25% 时间点还没有产出得分解剖和架构决策清单，请先提醒我，不要继续往下做。

## 汇报格式
每个阶段结束后，用简洁的报告回答：已确认的事实（附数据）、仍然是假设的事项、下一步实验和停止条件，以及哪些决策已经冻结、为什么。
```
